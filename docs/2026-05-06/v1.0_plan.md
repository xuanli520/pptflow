# p2r_tui v1.0: 并发流水线 + TUI 功能补齐 + 界面重设计

## 背景

p2r_tui 是一个 Go 写的 QA 编排 TUI（Bubble Tea + SQLite），对 AI 生成的交付包跑 6 阶段流水线（A-F）。当前可用但不完整：

1. **CLI 依赖**：`--extra-docs`（Codex 审查用的补充文档）、`--from`（指定起始阶段）、`--keep-runtime` 在 TUI 里没有入口
2. **单线程执行**：`Runner.Run()` 在一个 goroutine 里串行跑完，TUI 用 `running bool` 锁住整个界面
3. **无调度器**：一次只能跑一个流水线，没有队列和 worker pool
4. **DB 单连接**：`SetMaxOpenConns(1)` 阻止了并发访问
5. **界面问题**：左侧面板溢出、颜色体系不完整、footer 不随焦点变化、evidence 区域不够突出
6. **Codex CLI 安全兼容性**：`--full-auto`/`--search` 黑名单和审批策略 fallback 已作为安全基线，需要在 v1.0 中保留并补足回归覆盖

---

## SQLite 多连接说明

`database/sql` 的 `*sql.DB` 内部管理着一个连接池——`sql.Open` 一次拿到一个 handle，但底层可以有多个物理连接。当前 `SetMaxOpenConns(1)` 是人为限制：

- 改为 8 后，**读操作**可以在多个连接上并发（WAL 模式支持读写并发，但 SQLite 仍只有一个 writer）
- **写操作**由 SQLite 自身串行化——同时写可能返回 `SQLITE_BUSY`；必须确保每个物理连接都设置 `busy_timeout=5000ms`
- 应用层加 `writeMu` 是提前排队，避免进 SQLite 层再 busy-wait 浪费 CPU

不需要多个 `*sql.DB` 实例，同一个 handle + 扩大连接池即可。注意：`PRAGMA busy_timeout` 是连接级设置，不能只在 `Open()` 后用一次 `handle.Exec()` 期望覆盖后续新建连接。使用 modernc sqlite DSN `_pragma` 参数（例如 `file:<db>?_pragma=busy_timeout(5000)&_pragma=journal_mode(WAL)&_pragma=synchronous(NORMAL)`）或等价的每连接初始化方式。

## 实施计划

### Phase 1: DB 层并发改造 (`internal/db/store.go`)

- 加 `sync.Mutex writeMu` 到 Store
- 加 `withWriteTx(ctx, fn)` helper：lock → begin tx → run fn → commit
- SQLite 打开方式改为 URI/DSN `_pragma`，确保 `busy_timeout`、`journal_mode=WAL`、`synchronous=NORMAL` 对连接池中新建的每个物理连接生效；保留 `configureSQLite()` 作为兼容校验可以，但不能只依赖它
- 5 个写方法走锁：
  - `UpsertProjects` → `withWriteTx`
  - `CreateRun` → `withWriteTx`
  - `FinishRun` → `withWriteTx`
  - `PutStage` → `writeMu.Lock()`（单条 ExecContext，不需要显式 tx）
  - `InsertFindings` → `withWriteTx`（批量写入一个事务）
- 连接池：`SetMaxOpenConns(8)`, `SetMaxIdleConns(3)`

### Phase 2: Pipeline 进度回调 (`internal/pipeline/pipeline.go`)

纯增量改动，不影响 CLI 路径：

```go
type RunProgress struct {
    RunID, TaskID, Stage string
    Event string // run_created, stage_running, stage_done, cleanup, run_done, run_crashed
    StageRecord model.StageRecord
    Done bool
    Err  error
}
type ProgressReporter func(RunProgress)
```

- `RunOptions` 加 `Progress ProgressReporter` 字段
- `Runner.Run()` 内部仍负责生成 `runID`；外部 scheduler 不预分配 runID
- 在 `CreateRun` 成功后立刻调用 `Event: "run_created"`，让 scheduler 将 `runID` 晚绑定到 `jobID`
- 初始 stage 记录写入后、每个 stage 进入 running 状态后、每个 stage 执行完（`PutStage` + `InsertFindings` 之后）、cleanup 后都调用 `opts.Progress(...)`
- Run 正常结束、错误退出、panic/crash 恢复路径也调用，`Done: true`
- CLI 模式不设 Progress → `nil`，行为不变

### Phase 3: 调度器 (`internal/scheduler/scheduler.go` — 新包)

核心数据结构：
```go
type JobState int  // JobQueued, JobRunning, JobDone, JobFailed

type Job struct {
    JobID, RunID, TaskID string
    State         JobState
    CurrentStage  string
    Stages        []model.StageRecord
    Result        *pipeline.Result
    Err           error
    cancel        context.CancelFunc
    mu            sync.RWMutex
}

type JobSnapshot struct {
    JobID, RunID, TaskID string
    State                JobState
    CurrentStage         string
    Stages               []model.StageRecord
    Result               *pipeline.Result
    Err                  string
}

type Scheduler struct {
    store       *db.Store
    cfg         config.Config
    maxParallel int           // 来自 cfg.Pipeline.MaxConcurrent，默认 3
    sem         chan struct{} // buffered, cap = maxParallel
    mu          sync.Mutex
    jobs        []*Job
    jobByID     map[string]*Job
    activeByTask map[string]*Job
    notifyCh    chan struct{}
    closed      bool
}
```

关键方法：
- `Submit(taskID, opts) (jobID, error)` — 同 taskID 已有 queued/running job 则拒绝；创建 jobID 后立即返回；非阻塞获取 sem，成功则起 goroutine，失败则入队列
- `Snapshot() []JobSnapshot` — 线程安全拷贝，给 TUI 渲染用；不要按值复制包含 mutex 的 `Job`
- `NotifyCh() <-chan struct{}` — 状态变化时触发；`notifyCh` 容量为 1，发送必须使用非阻塞 `select { case ch <- struct{}{}: default: }`
- `Shutdown(ctx) error` — 优雅关闭：停止接受新任务，取消 queued/running job 的 context，等待运行中的 goroutine 退出或 ctx 超时

runJob goroutine 内：为 job 创建 cancellable context → 构建带 Progress 回调的 RunOptions → `runner.Run()` → `defer recover` 捕获 panic 并标记 `JobFailed` → 完成后检查队列是否有等待 job → 有则传递槽位，无则释放 sem。无论正常、错误、panic、取消，都必须释放 semaphore、从 `activeByTask` 移除、触发 notify。

Progress 回调闭包捕获 `jobID`，用 `RunProgress.RunID` 晚绑定真实 `runID`；`Event: "stage_running"` 更新 `CurrentStage`，`Event: "stage_done"` 更新对应 `StageRecord`，`Done: true` 设置终态。

- Space 切换开关（阶段多选、保留运行时）
- 上下键 在阶段列表中移动

## 关键设计决策

1. **写锁而非仅靠 SQLite busy_timeout**：Go mutex 避免 busy-wait CPU 消耗。每个 run 约 6 次写操作，各 stage 执行耗时以分钟计——锁竞争可忽略。

2. **Scheduler 独立包**：封装并发策略、job 生命周期和队列。TUI 只负责展示。依赖方向清晰：scheduler → db + pipeline，绝不反向。

3. **Progress 回调而非 channel**：每个 pipeline goroutine 持有自己的闭包，无 channel 生命周期管理。回调只更新对应 Job 状态并非阻塞 notify；`RunID` 由 `run_created` progress 晚绑定。

4. **文本输入复用托管附件，而非文件树选择器**：MVP 仍使用路径输入，但添加时调用 `taskdocs.Attach` 复制到托管 docs store，保证复现性。完整目录遍历 filepicker 后续可加，接口一致。

5. **runConfig struct 替代 confirm bool**：静态确认框无法支持交互式 stage 切换、路径输入和模式切换。

6. **`--from` 与显式多选互斥**：两者都是 stage selection source，不能同时存在。UI 层禁用另一组选项，提交层再次校验，pipeline options 只传其中一种。
